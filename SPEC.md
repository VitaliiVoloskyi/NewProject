# Meetings App — Specification

## 1. Overview

A small web application for managing meetings. A user can view the list of meetings, create a new meeting, and delete a meeting. Each meeting has a title, a description, a set of participants, a time, and a place. A participant can take part in many meetings, and a meeting can have many participants (many-to-many).

The project is a monorepo with a FastAPI backend, a React + shadcn/ui frontend, and a PostgreSQL database, all run together with Docker Compose and driven by a Makefile.

## 2. Scope

### In scope
- List meetings (sorted by start time, soonest first).
- Create a meeting.
- View a meeting's details and edit it.
- Delete a meeting (with a confirmation step in the UI).
- List participants and create a participant (needed to assign participants to meetings).
- Running the whole stack with one command (`make up`).

### Out of scope (v1)
- Authentication and user accounts.
- Editing or deleting participants.
- Recurring meetings, time-zone preferences per user, notifications, calendar sync.
- Pagination (the list is expected to be small; can be added later).

## 5. Data model

### Entities

**Meeting**

| Field | Type | Constraints |
|---|---|---|
| id | uuid | PK, generated by the backend (`uuid4`) |
| title | varchar(200) | required, non-empty |
| description | text | optional, default `""` |
| starts_at | timestamptz | required |
| ends_at | timestamptz | required, must be after `starts_at` |
| place | varchar(200) | required, non-empty (free text: room, address, or video link) |
| created_at | timestamptz | server default `now()` |

**Participant**

| Field | Type | Constraints |
|---|---|---|
| id | uuid | PK, generated by the backend (`uuid4`) |
| name | varchar(100) | required, non-empty |
| email | varchar(255) | required, unique, valid email |
| created_at | timestamptz | server default `now()` |

**meeting_participants** (association table)

| Field | Type | Constraints |
|---|---|---|
| meeting_id | uuid | FK → meetings.id, `ON DELETE CASCADE` |
| participant_id | uuid | FK → participants.id, `ON DELETE CASCADE` |
| | | PK (meeting_id, participant_id) |

### ER diagram

```
┌────────────┐       ┌──────────────────────┐       ┌──────────────┐
│  meetings  │ 1   * │ meeting_participants │ *   1 │ participants │
│────────────│───────│──────────────────────│───────│──────────────│
│ id (PK)    │       │ meeting_id (FK, PK)  │       │ id (PK)      │
│ title      │       │ participant_id(FK,PK)│       │ name         │
│ description│       └──────────────────────┘       │ email (UQ)   │
│ starts_at  │                                      │ created_at   │
│ ends_at    │                                      └──────────────┘
│ place      │
│ created_at │
└────────────┘
```

Deleting a meeting removes its rows in `meeting_participants` but never deletes participants.

The schema is created and changed only through Alembic migrations. The backend container runs `alembic upgrade head` on start.

## 6. Backend API

Base path: `/api`. All request and response bodies are JSON. Datetimes are ISO 8601 with a time-zone offset; the backend stores and returns UTC. FastAPI's OpenAPI docs are available at `/api/docs`.

### Endpoints

| Method | Path | Description | Success |
|---|---|---|---|
| GET | `/api/health` | Liveness check, also checks the DB connection | 200 `{"status": "ok"}` |
| GET | `/api/meetings` | List all meetings with their participants, ordered by `starts_at` ascending | 200 `Meeting[]` |
| GET | `/api/meetings/{id}` | Get one meeting | 200 `Meeting` |
| POST | `/api/meetings` | Create a meeting | 201 `Meeting` |
| PUT | `/api/meetings/{id}` | Replace a meeting's fields and participants (same body and rules as POST) | 200 `Meeting` |
| DELETE | `/api/meetings/{id}` | Delete a meeting | 204 |
| GET | `/api/participants` | List all participants, ordered by name | 200 `Participant[]` |
| POST | `/api/participants` | Create a participant | 201 `Participant` |

### Schemas

`MeetingCreate` (request):
```json
{
  "title": "Sprint planning",
  "description": "Plan sprint 12",
  "starts_at": "2026-09-22T10:00:00+03:00",
  "ends_at": "2026-09-22T11:00:00+03:00",
  "place": "Room 204",
  "participant_ids": [
    "3f2b8c1e-6a4d-4e2f-9b7a-1c5d8e9f0a12",
    "b7e4a9d2-1f3c-4a8b-8e6d-2c9f7a1b3d45"
  ]
}
```

`Meeting` (response):
```json
{
  "id": "9c1d2e3f-4a5b-4c6d-8e7f-0a1b2c3d4e5f",
  "title": "Sprint planning",
  "description": "Plan sprint 12",
  "starts_at": "2026-09-22T07:00:00Z",
  "ends_at": "2026-09-22T08:00:00Z",
  "place": "Room 204",
  "participants": [
    {"id": "3f2b8c1e-6a4d-4e2f-9b7a-1c5d8e9f0a12", "name": "Olena Koval", "email": "olena@example.com"},
    {"id": "b7e4a9d2-1f3c-4a8b-8e6d-2c9f7a1b3d45", "name": "Taras Shevchuk", "email": "taras@example.com"}
  ],
  "created_at": "2026-09-21T09:15:00Z"
}
```

`ParticipantCreate` (request): `{"name": "Olena Koval", "email": "olena@example.com"}`

`Participant` (response): `{"id": "3f2b8c1e-6a4d-4e2f-9b7a-1c5d8e9f0a12", "name": "Olena Koval", "email": "olena@example.com"}`

### Validation and errors

| Case | Status |
|---|---|
| Missing/empty `title` or `place`, invalid datetime, `ends_at <= starts_at`, invalid email | 422 (FastAPI validation format) |
| `participant_ids` contains an id that does not exist | 422 with message listing the unknown ids |
| Duplicate ids in `participant_ids` | de-duplicated silently |
| `{id}` in the path is not a valid UUID | 422 |
| Meeting not found on GET/DELETE | 404 `{"detail": "Meeting not found"}` |
| Participant email already exists | 409 `{"detail": "Participant with this email already exists"}` |

A meeting with zero participants is allowed.

### Other backend requirements
- IDs are UUIDs: PostgreSQL `UUID` columns, SQLAlchemy `Uuid` type, Pydantic `uuid.UUID`; serialized as strings in JSON.
- Configuration from environment variables: `DATABASE_URL`, `CORS_ORIGINS`.
- CORS enabled for the Vite dev server origin (`http://localhost:5173`) so the frontend can run outside Docker during development.
- Meeting queries load participants eagerly (`selectinload`) to avoid N+1 queries.

## 7. Frontend

Built with shadcn/ui components; routing with `react-router`.

### Routes and auth

| Path | Page | Access |
|---|---|---|
| `/` | redirects to `/home` | — |
| `/home` | Meetings (below) | signed in; otherwise a signed-out page with **Sign in** (and **Continue with Google**), then back |
| `/profile` | Profile (below) | same as `/home` |
| `/login` | Redirects straight to Cognito's managed login; signed in: to `/home` | anyone |
| `/auth/callback` | Cognito returns here with a code; swapped for tokens, then back to where the user started | — |
| `/signup` | redirects to `/login` (managed login has "Create an account") | — |
| anything else | redirects to `/home` | — |

- **Sign-in** is Cognito's managed login (v2), not our own forms: email + password, sign-up with the emailed code, password reset, and **Continue with Google** all live there. The app uses `react-oidc-context` / `oidc-client-ts`: authorization code flow with PKCE from a public client; tokens in `localStorage`, renewed with the refresh token. A login must start on `/login` (the library stores the `state` and PKCE verifier that `/auth/callback` checks).
- **Sign out** clears the local session, then goes to Cognito's `/logout?client_id=…&logout_uri=<origin>/` (Cognito has no OIDC end-session endpoint).
- Forms use react-hook-form + zod. Errors appear under the fields; a failed request shows its message above the submit button.
- The meetings top bar shows the user's initial (name and email on hover; links to `/profile`) and a **Sign out** button.
- **Profile** (`/profile`): a back arrow to `/home`, the user's initial, name and email, then one card per change. The changes go to Cognito's user API directly with the access token (scope `aws.cognito.signin.user.admin`); the app then refreshes the tokens, and the backend copies the new name and email from the ID token on the next request.
  - **Name**: prefilled; **Save name** is enabled once it changes.
  - **Email**: a new email, then the code Cognito sends to it (**Verify email**, **Send a new code**, **Cancel**). The email changes only after the code is entered (`AttributesRequireVerificationBeforeUpdate` in `infra/auth.yaml`).
  - **Password**: current password, new password (min 8 characters), confirm (must match). A wrong current password shows "Current password is wrong".
  - Google accounts cannot edit anything here (Google sets the name and email at every sign-in); the page says so instead of showing the forms.
  - A **Sign out** button at the bottom.
- The signed-out pages fit one screen without scrolling, down to 360×640. On short viewports (≤ 700px tall, the `short:` variant) the subtitle is hidden and spacing tightens.
- Deep links need an `index.html` fallback: nginx has `try_files`, and CloudFront maps 403/404 to `/index.html`.

### Main page: Meetings (`/home`)

- **Header** with the app name and an **"Add meeting"** button.
- **Layout** (like Google Calendar): the page fills the viewport. One compact top bar holds the app name, **Today** ‹ › with the visible date range, a List / Day / Week switcher (Radix `ToggleGroup`; icons only on phones), **Add meeting**, and the user's initial with a **Sign out** button. The active view fills the rest of the screen and scrolls inside it. List and Week move by 7 days, Day by 1. The app opens on today. Weeks start on Monday.
- **List view** — the anchor day ±3 days (7 days), grouped by date. Each day has a heading (weekday, date, "Today" badge) and its meetings, or "No meetings". Each row shows:
  - the time on that day (`10:00–11:00`; a meeting that spans several days shows `from 18:00`, `until 09:00` or `All day`, and appears on every day it touches),
  - title, with the description as secondary text (truncated),
  - place,
  - participants as `Badge`s (show the first 3, then `+N`),
  - **edit** and **delete** icon buttons.

  Each day heading has a **+ Add** button that opens the Add meeting dialog for that day. The start is 10:00, or the next full hour if that is later today.
- **Day view / Week view** — a time grid with one column per day. The grid shows all 24 hours in its own scroll area, with sticky day headings. It opens scrolled to the current time when today is visible, otherwise to 08:00 or the first earlier meeting. Titles of long meetings stay visible while scrolling, and short meetings show the title and time on one line. Overlapping meetings sit side by side. Today's column is tinted and has a current-time line. Clicking a meeting opens its details. Clicking an empty spot opens the Add meeting dialog with the date and a 1-hour slot starting at that time (rounded down to 30 minutes, cut off at 23:59). Hovering previews the slot as a dashed `+ 16:30` block. In the week view, clicking a day heading opens that day. On narrow screens the week scrolls horizontally.
- Times use the browser's local time zone. All views filter the `GET /api/meetings` result on the client.
- **Empty state**: "No meetings yet" with an "Add meeting" button.
- **Loading state**: `Skeleton` rows. **Error state**: `Alert` with a retry button.

### Add meeting dialog

A shadcn `Dialog` containing a form (react-hook-form + zod, same rules as the backend):

| Field | Component |
|---|---|
| Title | `Input` (required) |
| Description | `Textarea` |
| Date | `Popover` + `Calendar` |
| Start time / End time | `Input type="time"` (end must be after start) |
| Place | `Input` (required) |
| Participants | multi-select combobox (`Popover` + `Command`) listing existing participants, with selected ones shown as removable `Badge`s |

The participants combobox includes a **"+ New participant"** option that opens a small inline form (name, email) and, on save, calls `POST /api/participants` and selects the new participant.

On submit: `POST /api/meetings`; on success close the dialog, refresh the list, and show a success toast (`Sonner`). Backend 422/409 errors are shown next to the relevant field or as a toast.

### Meeting details and editing

Clicking a meeting (list row or calendar block) opens a details `Dialog` showing the title, time, place (a link if it is a URL), description, and participants with their emails, plus **Edit** and **Delete** buttons. Each row/card also has its own **Edit** (pencil) and **Delete** icon buttons.

Edit reuses the Add meeting dialog, prefilled, titled "Edit meeting", with a "Save changes" button. On submit: `PUT /api/meetings/{id}`; on success close the dialog, refresh the list, and show a success toast.

Dialogs never exceed the viewport height: the header and footer stay fixed and the body scrolls.

### Delete meeting

Clicking delete opens an `AlertDialog` ("Delete meeting "<title>"? This cannot be undone."). Confirming calls `DELETE /api/meetings/{id}`, removes the meeting from the list, and shows a toast.

### Data access
- All API calls go through `src/lib/api.ts` using relative URLs (`/api/...`).
- In Docker, nginx proxies `/api` to the backend. In local dev, Vite's `server.proxy` does the same.
- TanStack Query keys: `["meetings"]`, `["participants"]`; mutations invalidate the matching key.

## 8. Docker Compose

`docker-compose.yml` defines three services:

| Service | Image / build | Ports | Notes |
|---|---|---|---|
| `db` | `postgres:17-alpine` | `${DB_PORT:-5432}:5432` | named volume `pgdata`; healthcheck with `pg_isready` |
| `backend` | `./backend` | `8000:8000` | `depends_on: db (service_healthy)`; runs `alembic upgrade head` then `uvicorn app.main:app --host 0.0.0.0 --port 8000` |
| `frontend` | `./frontend` (multi-stage: node build → nginx) | `3000:80` | nginx serves static files and proxies `/api` to `backend:8000` |

Environment comes from a root `.env` file (copied from `.env.example`):

```
POSTGRES_USER=meetings
POSTGRES_PASSWORD=meetings
POSTGRES_DB=meetings
DB_PORT=5432
DATABASE_URL=postgresql+asyncpg://meetings:meetings@db:5432/meetings
CORS_ORIGINS=http://localhost:5173,http://localhost:3000
```

After `make up`, the app is available at `http://localhost:3000` and the API docs at `http://localhost:8000/api/docs`.

## 10. Testing

Backend (pytest, httpx `AsyncClient`, separate test database):
- create meeting with participants → 201, participants returned;
- create meeting with `ends_at <= starts_at` → 422;
- create meeting with unknown participant id → 422;
- list meetings is sorted by `starts_at`;
- delete meeting → 204, then GET → 404; participants still exist;
- delete non-existent meeting → 404;
- create participant with duplicate email → 409.

Frontend: manual check against the acceptance criteria below (automated UI tests are optional for v1).

## 11. Acceptance criteria

1. On a clean machine with Docker installed, `make env && make up` starts the database, backend, and frontend; `http://localhost:3000` shows the meetings page.
2. The user can create participants and a meeting with title, description, date/time range, place, and several participants; the meeting appears in the list without a page reload.
3. The same participant can be added to several meetings.
4. The user can delete a meeting after confirming; it disappears from the list and its participants remain available.
5. Invalid input (empty title, end before start, bad email) is rejected with a visible message in the UI and a 4xx response from the API.
6. Data survives `make down && make up`.
7. `make test` and `make lint` pass.
