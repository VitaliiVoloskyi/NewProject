# 7. Describe Cognito, the weekly report and the agenda parser in Terraform, run by HCP Terraform

Date: 2026-10-31 · Status: accepted

## Context

Labs 4–6 added three CloudFormation stacks: `spry-auth` (Cognito, 5 resources), `spry-reports`
(the weekly report, 14) and `spry-ai` (the agenda parser and the budget alarm, 7). They worked,
but three things pushed against them:

- **The project already reaches outside AWS.** The Google OAuth client, the GitHub repository and
  its branch rules, and a DNS provider are configured by hand. CloudFormation stops at the edge of
  one AWS account.
- **A second environment is coming** (staging, and maybe a white-label copy). With stacks, that
  is a second set of parameters passed by shell scripts, and the scripts decide what each stack
  receives.
- **Who changes what is unclear.** `make deploy-auth` and `make deploy-ai` ran from any laptop
  with admin keys, and `deploy-frontend` quietly redeployed the auth and AI stacks to update
  their URLs. No change was reviewed before it reached AWS.

The stacks hold data we must not lose: the user pool (every account) and the reports bucket.

## Decision

- **Terraform** describes those 26 resources, in `infra/auth.tf`, `reports.tf` and `ai.tf`. They
  became 38 Terraform resources, because S3 bucket settings and IAM attachments are separate
  resources in the AWS provider. The other stacks (network, API, database, ECR, site, GitHub
  OIDC) stay CloudFormation for now. Terraform reads their outputs with the
  `aws_cloudformation_stack` data source.
- **HCP Terraform** keeps the state (workspace `spry-dev`, Remote execution) and runs Terraform.
  It is connected to the repository with working directory `infra`. A pull request gets a
  speculative plan as a check, and a merge to `main` applies it.
- **No stored cloud keys.** Runs get an OIDC token from `app.terraform.io` and assume the role
  `spry-hcp-terraform` (`infra/bootstrap`, applied once from a laptop with local state). The
  role trusts only the workspace `spry-dev` of our organization.
- **Adopted, not re-created.** All 26 resources got `DeletionPolicy: Retain` before the stacks
  were deleted. Then `import` blocks handed them to Terraform. The import plan was 38 to import,
  0 to add, 0 to destroy, with two harmless in-place updates: the mailer's code was re-uploaded
  byte for byte, and the Google provider's client secret was marked sensitive in state. Nothing
  was re-created. Role names and permission statement IDs generated by CloudFormation are kept
  as literals, because a new name would mean a new resource.
- **Two roads.** HCP Terraform changes the infrastructure. GitHub Actions ships the code
  (`make deploy-backend`, which also points the builder and the parser at the new image).
  Terraform sets the functions' image only on creation (`ignore_changes = [image_uri]`), so the
  two roads never fight over one attribute.
- `prevent_destroy` guards the user pool and the reports bucket, which used to have
  `DeletionPolicy: Retain`.

## Alternatives

- **Keep CloudFormation.** AWS keeps the state and rolls back failed changes on its own, with
  nothing for us to host or protect. It cannot describe Google, GitHub or DNS, though, and the
  workflow had no plan step that a reviewer would read.
- **AWS CDK.** Real code (TypeScript or Python) on top of CloudFormation. It inherits the
  AWS-only limit and adds a build step. The team writes Python and TypeScript, but the
  infrastructure is small and declarative, and HCL is easier to review in a pull request than
  generated templates.
- **OpenTofu.** It accepts the same files and is open source (MPL), while Terraform is under the
  BSL since 2023. For a class project the licence does not matter, and the course uses HCP
  Terraform, which runs Terraform. The files keep both options open: switching is changing the
  binary and the state backend.
- **State in S3 with a lock file.** It costs nothing and is all in AWS. But someone still has to
  run `apply`, from a laptop or from CI, with the keys to do it. HCP Terraform adds runs, the plan
  check on pull requests, state history and dynamic credentials, on the free tier.

## Consequences

- **Who can change the infrastructure:** anyone who can get a pull request merged into `main`.
  Nobody needs AWS keys for it. HCP Terraform applies after the merge. `make infra-plan` runs a
  speculative plan from a laptop and changes nothing. There is no apply target in the Makefile.
  Applying from a laptop (a workspace in Local mode) is for emergencies only, and it is recorded
  in HCP Terraform anyway.
- **Where the secrets are.** The Google client secret is a sensitive, write-only variable of the
  workspace. Plans show `(sensitive value)`, but **the state holds it in plain text**, next to the
  database URL the report builder receives. The state is encrypted at rest in HCP Terraform, but
  anyone who can read it can read them: organization owners, and teams with state access. AWS
  holds them too (Cognito, the Lambda environment). No secret is in Git: `terraform.tfvars` has
  only non-secret values. Report recipients and the budget email are workspace variables, so that
  this public repository carries no personal addresses.
- **If HCP Terraform is down:** the application keeps running, because nothing in the request
  path depends on it. Code deploys from GitHub Actions read Terraform's outputs (Cognito ids,
  the parser's URL) from HCP Terraform, so they fail until it is back. Infrastructure changes
  wait. In an emergency, an owner can download the latest state version, switch to a local
  backend and apply with their own credentials, then upload the state back (`terraform state
  push`). It is the same "emergencies only" road as above, and the team has to agree on it.
- **Drift is visible.** Every plan compares the files with AWS. A fix made in the console at 23:00
  shows up in the next plan as a change to undo, so it must be followed by a pull request that
  makes the same change in the files.
- **Order between the two roads.** When a change needs both, such as a new environment variable
  that the code reads, the infrastructure goes first: merge, wait for the apply, then push the
  code. GitHub Actions does not wait for HCP Terraform on its own.
- **A new environment needs two applies.** `make deploy-backend` needs Cognito, and `reports.tf`
  needs the backend's network. The first run applies Cognito alone (`-target`), then comes the
  backend, then a full run. Splitting `infra/` into modules with one workspace per environment
  is the next step.
- **Origins are reviewed.** Cognito's callback URLs and the parser's CORS come from `app_urls` in
  `terraform.tfvars`. `make deploy-frontend` and `make add-domain` no longer change them. They
  print what to add, and the change goes through a pull request.
- **CI needs one HCP Terraform token** (the `TF_API_TOKEN` secret) to read outputs. That is the
  one long-lived credential we added. A team token with access to this workspace only is the
  narrowest choice.
